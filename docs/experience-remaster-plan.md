# 前端体验与标签流程重制计划

2026-10-23。研究由用户指定的 **GPT-6-Astra / Ultra** 完成；主代理核对源码与一手资料，并整理实施和验收要求。本文为计划，尚未实施整套新界面或更换模型。已完成的功能拆除另见本轮验收记录。

## 推荐方向

**同一浏览上下文中的标签式图片浏览。** 用户应能顺畅地找标签、组合条件、查看图片、补充条件并回到原位置，不需要反复理解页面之间的区别。已有虚拟图墙、灯箱、收藏、查询代次保护和任务持久化继续使用。

## 先理解优秀体验来自哪里

“macOS 26 的体验优秀”是用户的感受，不能直接推导为所有界面都更高效。Apple 的官方设计材料能够证明其设计意图，不能代替 illuTag 的用户测试。

Apple 的新设计系统强调内容与操作层的关系、结构和连续性；桌面紧凑控件仍适合高密度场景。Liquid Glass 的适应性也以可读性、内容层与控制层的区分为前提。参见 [设计系统](https://developer.apple.com/videos/play/wwdc2025/356/) 与 [Liquid Glass 原则](https://developer.apple.com/videos/play/wwdc2025/219/)。

据此对本产品作出的设计判断是：

- **减少重新理解**：相同操作在各处有相同含义，过滤条件、结果、焦点和返回位置保持对应。
- **让内容主导**：图片是浏览的主体，标签是定位图片的工具；导航、管理和技术状态按使用时机出现。
- **让动作有可靠回响**：先反馈请求已接收，再清楚交代成功、等待或失败；失败后仍能继续原任务。
- **照顾反复使用**：键盘路径、点击目标、滚动、窗口缩放、文字对齐和出错恢复，与首屏视觉同等重要。
- **整体协作**：缩略图、查询、模型和后台调度共同决定感受。单项吞吐更高，可能同时让前台更难用。

这些是本项目的推论与待验收原则。Windows / WebView2 是现有验收平台，应遵循用户熟悉的键盘和窗口习惯。材质效果需服从清晰度、对比度、减少动态效果偏好和运行成本。

## 连贯的目标操作

1. 在当前范围找标签；中文优先，英文原名用于稳定标识和必要辨认。标签目录中的查找文字与图片筛选条件分别保存。
2. 点击或键盘确认标签后加入交集，结果原地更新。浏览分组、收藏分组与排序不暗中清除已经选择的条件。
3. 请求期间有明确反馈；若保留旧图片，旧图片必须仍绑定原查询快照，不能被新条件冒名。允许继续操作，最新有效请求才发布新结果。
4. 打开图片后，图片序列、标签筛选和返回位置属于该次浏览快照。信息面板添加标签时，在当前上下文更新条件。
5. 关闭灯箱恢复原图附近与焦点。图片被删除或新结果不再包含原图时，采用邻近图片或列表起点等明确的回退规则。
6. 分页失败在结果末尾提供重试，不遮掉已有图墙；取消、离线或文件缺失的反馈不妨碍其他可用图片。

浏览位置的身份要包含结果条件与实际序列标识（例如随机种子），排除分页 offset；它与“选择作用域”的语义键用途不同，不能机械复用。标签目录的搜索、分组与排序也不能被误当作图片结果条件。

撤销删除继续遵循现有语义：恢复结果中的记录，不抢回用户已经切换的查看器图片。现有合成无界面回归已验证此行为，不应作为“缺少的功能”重做。

## 视觉与信息结构

- 保留一层主导航；标签浏览是找图工作区，维护操作集中到次要入口。任务状态提供简洁入口，详细历史按需打开。
- 图片结果保持主视觉面积。标签目录采用可调整且有边界的宽度；窄窗以互斥面板呈现，两个面板保留各自状态。
- 标签行固定为封面、名称、数量、操作四个区域：主名称清楚，英文次级，数量按列对齐；收藏、选中、焦点、悬停各有独立含义。
- 已选条件是查询的组成部分，靠近结果；条件过多时有可理解的折叠方式，不让多行工具栏挤走图片。
- 灯箱保留图片的完整比例；信息面板、缩放工具、缩略图条各有稳定区域。先保证输入、焦点、缩放和平移规则一致，再调整外观。
- 建立少量字号、间距、控件高度、色彩和焦点样式规则。中文主名称不被图标与数量挤成无法辨认的碎片；普通文本对比度以 [WCAG 2.2 AA 的 4.5:1](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) 为基线，大字适用相应标准。
- 动画只帮助理解位置和状态变化；尊重减少动态效果偏好。常用操作不能只在悬停时才有可发现入口。

以上是唯一推荐方案的约束，具体像素宽度和密度应在实际窗口与长标签样本中验证后确定。Apple 的 [搜索设计指导](https://developer.apple.com/design/human-interface-guidelines/searching) 和 [macOS 设计指导](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos/) 作为参照，不将原生 API 的便利直接等同于当前技术栈已经具备相同能力。

## 性能：测使用路径，而不只测吞吐

固定目标机器、系统缩放、窗口大小、素材清单和后台负载。分别记录冷启动/冷缓存与预热结果，记录中位数、P95、最慢值、错误与采样间隔；优化前后使用相同条件。

| 场景 | 记录内容 | 验收原则 |
|---|---|---|
| 标签输入与选择 | 按键到反馈、建议到达、IME、过期建议、焦点 | 候选交互反馈 P95 100ms 内作为初始目标；不能把去抖时间与查询耗时混在一起 |
| 组合条件与首屏 | 本地状态、IPC、数据库查询、缩略图解码分别计时 | 先显示接收反馈；不预先承诺所有磁盘和冷缓存都能在固定时间加载完成 |
| 连续滚动 | 帧间隔、超过 50ms 的长任务、DOM/已解码图片量、内存 | 60Hz 基准以接近 16.7ms 帧预算为目标；DOM 和解码资源随视口/有限预取有界 |
| 看图往返 | 原图就绪时间、图片 ID 锚点、偏移、焦点、标签和范围 | 往返不需要重新找原图；不可用原图有可恢复反馈 |
| 后台打标时浏览 | 上述指标与 CPU、GPU、磁盘占用 | 保留前台响应；批量吞吐不能单独作为采用依据 |
| 长会话 | 50 次查询/往返、长滚动后资源平台与清理 | 区分受控缓存平台、内存泄漏和测量误差，不以任意进程上限掩盖问题 |

100ms 等为待基线修订的候选预算，不是本轮实测。记录 Rust、WebView2、Python 和 GPU 的资源口径，不能把其中一个进程的采样峰值当作整套应用峰值。

百万图片以隔离合成元数据验证查询和分页规模；高分辨率以有限且代表性的素材验证解码、视口、灯箱与模型输入。合成素材不证明真实标签准确率，也不需要为每次界面修复生成百万张高分辨率原图。

## 标签流程与模型优化

先为每次推理建立内部可复现记录：权重与词表版本/摘要、类别映射、图像方向和透明处理、色彩空间、缩放/填充、归一化、通道/张量布局、输出变换、实际阈值、运行后端。它服务于维护与验证，不把技术参数堆进日常浏览界面。

使用可控的小图验证预处理张量，使用假服务验证读写、EOF、重试、取消和保存次数；这些检查不依赖真实图库，也不能替代模型语义评估。

人工修正应独立于模型结果：用户确认或排除的标签不能在重打标后悄悄恢复成相反结果。先设计来源和优先级，再决定所需最小数据变更；未验证前不贸然升级主库。

用户启动导入/处理后，应尽早得到可浏览结果，标签随有效处理完成而可用；区分尚未处理与确实没有标签。暂停或重试不阻断已完成图片的浏览，不因计划改造自动启动正式图库任务。仅在源或模型契约失效时重处理对应内容。

语义评估需要经授权的分层样本：常用和长尾标签、角色/作品、画面细节、中英同义与歧义、不同图片风格、难例和可接受的“不确定”。当前尚未确认可用标注集，可先制定标注协议和建立小规模种子集，再逐步扩展；样本按来源/作品划分，避免相近样本跨训练/校准/验收集合泄漏。

采用每类 precision/recall、漏标与误标类型、中文映射错误和实际找图任务成功率；微平均不能掩盖长尾失败。阈值选择必须体现误标与漏标的代价。网络原始分数不能直接保证同等正确概率；校准是需要独立验证的步骤，参见 [Guo 等人的原始研究](https://proceedings.mlr.press/v70/guo17a.html)，不直接套用其方法宣称本模型已经校准。

封面资格、检索召回和自动标签发布的用途不同，应分别验证阈值；不能用一个更高分数掩盖漏标，也不能把现有封面高分规则宣称为真实正确率保证。先在内部核实规则，日常界面保持清楚克制。

在同一套样本上比较当前基线与候选模型的标签覆盖、找图效果、延迟、内存/显存、包体与许可；优先少量有理由的候选。有证据表明替换有收益才切换，现有结果不因实验整库失效或强制重打。

运行时先测现状，再对线程数、并发、批大小和自旋策略做受控比较，观察后台吞吐及前台损失。ONNX Runtime 的 [线程管理文档](https://onnxruntime.ai/docs/performance/tune-performance/threading.html) 明确存在资源/延迟取舍；不以“开满线程”作为统一优化。

## 分批实施与完成标准

| 批次 | 实施内容 | 交付与通过条件 |
|---|---|---|
| P0 基线与契约记录 | 固定安全素材、查询脚本、焦点/锚点记录，分解耗时；核实当前模型静态契约 | 输出可重复基线、已确认问题清单和未知项；不读取生产权重或自动跑正式图库 |
| P1 操作连续性 | 搜索建议键盘与提交、请求/显示快照、分页错误保图、完整查询身份与图片锚点 | 快速切条件、慢响应、失败重试、看图返回、删除后撤销在 1430/768/500 宽度通过 |
| P2 共享结果与视觉 | 共享结果加载/分页/虚拟化内核，保留标签目录独立状态；统一列表、工具层级与灯箱细节 | 长滚动资源有界，普通图库和标签结果行为一致，键盘与对比度合格，无新常驻工具区 |
| P3 标签可靠流程 | 合成张量/假服务契约、人工修正优先级、版本化结果与失败恢复 | 已确认的模型输入可复现；重打标不覆盖人工意图；中断重试不重复或丢保存 |
| P4 有证据的模型实验 | 建立分层真值、校准与少量候选比较，验证前后台资源取舍 | 达到任务效果与资源预算才采用；报告样本和未覆盖域，支持受控切换 |

P0～P1 是下一批实现重点。P2 在状态语义稳定后进行；P3 的契约核实可与前端基线并行。P4 依赖评估条件，不阻塞界面工作。

每批都以用户能实际完成的路径验收。先修复一个连续流程并证实改善，再进入下一批；不以新页面或新模式填充路线。
